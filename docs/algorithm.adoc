= How spark-lp solves models
:toc: left
:source-highlighter: highlightjs

spark-lp first converts an `LpProblem` into the numerical form required by its continuous solver. A
model containing `Integer` or `Binary` variables adds a branch-and-bound search around repeated
continuous solves.

This guide explains solver behavior that affects configuration, memory use, reported status or solve
evidence. See xref:usage.adoc[the usage guide] for the modelling and result APIs.

The equations below use these terms:

[cols="1,3",options="header"]
|===
|Term |Meaning
|Original model |The variables, bounds, constraints and objective supplied through `LpProblem`.
|Internal model |The equality-form problem produced for the numerical solver.
|Row |One equality in the internal model.
|Right-hand side (RHS) |The value on the right of an equality, written as `b`.
|Primal variables |The internal variable values, written as `x`.
|Dual variables |The equality multipliers `lambda` and nonnegative bound multipliers `s`.
|Residual |A numeric error in feasibility, stationarity or objective agreement; smaller is better.
|Stationarity |The requirement that objective, constraint and bound effects balance at a solution.
|LP relaxation |A mixed-integer model solved temporarily without requiring whole-number values.
|Incumbent |The best integer-feasible solution found so far.
|Certificate |Numeric evidence supporting an infeasible or unbounded result.
|===

The continuous solver minimizes `c^T*x` subject to `A*x = b` and `x >= 0`. Here `A` is the
internal constraint matrix and `c` contains the linear objective coefficients. A continuous convex
quadratic model adds `0.5*x^T*Q*x` to the objective.

== From `LpProblem` to equality form

`LpCompiler` validates Spark keys and coefficients, applies automatic simplification (presolve),
then converts every variable and constraint to the nonnegative equality form used by the continuous
solver:

[source,mermaid]
----
flowchart LR
  M[Original model and Spark data] --> V[Validate keys and coefficients]
  V --> P[Fold fixed variables and shift bounds]
  P --> E[Check empty rows and exact duplicate equalities]
  E --> A[Add inequality and upper-bound slacks]
  A --> C[Build distributed sparse columns and objective]
  C --> L[Continuous LP or integer search]
  L --> R[Undo transformations and report diagnostics]
----

[cols="1,2",options="header"]
|===
|Original declaration |Internal representation
|`x >= l` |`x = l + y`, `y >= 0`. Subtract each coefficient times `l` from the corresponding RHS and add `c*l` to the objective constant.
|`l <= x <= u` |After the lower-bound shift, add `y + slack = u - l`, with `slack >= 0`.
|`x = l = u` |Remove `x` and substitute `l` into its constraints and objective.
|No lower bound on `x` |Replace `x` with `positive - negative`, where both new variables are nonnegative.
|`expression <= b` |Add a nonnegative slack variable: `expression + slack = b`.
|`expression >= b` |Add a nonnegative slack variable: `expression - slack = b`.
|Maximize |Negate the objective before solving and restore its original sense in the result.
|===

Example: minimize `2*x + 7` with `5 <= x <= 10` becomes minimize `2*y + 17` with `y + slack = 5`;
`y = 0` reconstructs `x = 5`, cost `17`.

The internal matrix is stored by distributed sparse columns as `AT = A^T`. Original variables follow
declaration order; keys in a variable set follow encoded-key order. Rows follow constraint declaration
order and then group-key order. Duplicate detection first hashes candidate rows, then compares their
normalized coefficients before merging them; a hash match alone never merges rows. Contradictory
declared bounds, inconsistent duplicate equalities and impossible constant rows raise
`LpModelException` before numerical optimization.

== Continuous interior-point solve

spark-lp uses a primal-dual predictor-corrector interior-point method. It initializes `x` and `s`
strictly above zero, then computes an affine predictor direction and a centered corrector direction
in each iteration.

[source,mermaid]
----
flowchart TD
  I[Initialize positive x and s] --> R[Compute primal and dual residuals]
  R --> W[Update mu and diagonal weights]
  W --> P[Solve affine predictor]
  P --> C[Choose centering and solve corrector]
  C --> U[Step while keeping x and s positive]
  U --> T{Residuals below tolerance?}
  T -->|Yes| O[Optimal]
  T -->|No| F{Infeasibility certificate?}
  F -->|Yes| S[Report certificate status]
  F -->|No| B{Iteration budget left?}
  B -->|Yes| R
  B -->|No| L[IterationLimit]
----

Each iteration sets `mu = x^T*s/n`, where `n` is the number of internal variables, and
`D2 = diag(x/s)` with guarded inverses. Both Newton directions solve
`A*D2*A^T*deltaLambda = rhs`. The affine predictor sets
`sigma = min(1, (muAffine/mu)^3)`; the corrector adds centering and a second-order correction, and
the step uses `etaIteration` to stay inside the nonnegative cone. The predictor-corrector
formulation follows Cui et al. <<cui2019>> (section 2.1).

Convergence requires all three normalized residuals below `SolveConfig.tolerance`:

....
primal = ||A*x - b||_2 / (1 + ||b||_2)
dual   = ||A^T*lambda + s - c||_2 / (1 + ||c||_2)
gap    = |c^T*x - b^T*lambda| / (1 + |b^T*lambda|)
....

Every primal row must also satisfy `abs((A*x-b)_i)/(1+abs(b_i)) < tolerance`, so an
unrelated large right-hand side cannot hide an inaccurate constraint.

`SolveConfig.infeasibilityTolerance` controls two certificate tests. A primal-infeasibility
certificate is a normalized multiplier `y` satisfying
`A^T*y <= infeasibilityTolerance` and `b^T*y = 1`. An unbounded direction is a nonnegative `z`
satisfying `||A*z||_inf <= infeasibilityTolerance` and improving the objective. The solver reports
unboundedness only when it also has a primal-feasible point. Certificate tests use the last completed
iterate and account for floating-point tolerance. Acceptance also checks homogeneous residuals and
a significant separation margin in equilibrated certificate coordinates. Primal multipliers are
scaled by their row coefficients and RHS; primal directions are scaled by their column coefficients
and cost. The invariant scales are prepared once per solve. These checks prevent large objective or
RHS units from turning a nonzero equation into a certificate, while preserving unrelated zero
certificate entries. Certificates remain numerical witnesses, not exact-arithmetic proofs.

== Choosing the Newton-system solver

The predictor and corrector each solve linear equations based on `A*W*A^T`, called the Gramian,
where `W` is a positive diagonal matrix. `SolveConfig.newtonSolver` selects how those equations are
solved. Here `m` is the number of internal equality rows after adding upper-bound and constraint
slacks.

[cols="1,3,2",options="header"]
|===
|`NewtonSolver` value |Behavior |Driver memory
|`Auto` |Use `Cholesky` when `m <= min(10000, maxLocalConstraints)`; otherwise use `ConjugateGradient`. |Depends on the selected method.
|`Cholesky` |Collect the Gramian, factor its exactly disconnected row blocks on the driver and reuse the factors for predictor and corrector. |About `16*m*m` bytes for the Gramian, plus aggregation buffers.
|`ConjugateGradient` |Apply `v -> A*(W*(A^T*v)) + Rd*v` through Spark without collecting the Gramian. |Driver vectors plus about `32*m*rank` bytes for the preconditioner.
|===

The 10000-row `Auto` cutoff is a conservative policy, not a universal performance crossover.
`SolveConfig.maxLocalConstraints` also acts as the safety cap for explicit `Cholesky`. Selecting
`Cholesky` above 10000 rows therefore requires raising the cap; raising the cap alone does not
change `Auto`'s 10000-row cutoff.

At `m = 10000`, the Gramian estimate is about 1.6 GB and executor aggregation buffers add roughly
400 MB. Packed Cholesky arrays impose a separate 65535-row limit. CG avoids the Gramian allocation,
but the driver still retains row metadata, the RHS, residual vectors and group keys. One CG operator
application streams all stored sparse columns, so Spark scheduling affects its cost more strongly.
See xref:benchmarks.adoc[the benchmark methodology] for workload-specific comparisons.

=== Conjugate-gradient equations and configuration

With `rb = A*x-b`, `rc = A^T*lambda+s-c` and `q` as the RHS that controls the products
`x_i*s_i` (complementarity), the CG backend solves:

[source,text]
----
A*dx + Rd*dLambda = -rb
A^T*dLambda + ds - Rp*dx = -rc
S*dx + X*ds = q

W = (S/X + Rp)^(-1)
h = rc + q/x
(A*W*A^T + Rd)*dLambda = -rb - A*W*h
dx = W*(A^T*dLambda + h)
ds = -rc - A^T*dLambda + Rp*dx
----

`Rp` and `Rd` are positive diagonal regularization entries. They improve conditioning of the
Newton system but do not change the convergence tests, which are recomputed from the unregularized
internal model. The matrix-free regularization and preconditioning follow Gondzio
<<gondzio2012>> (sections 3–6).

[cols="2,1,3",options="header"]
|===
|API setting |Default |Effect
|`SolveConfig.cgTolerance` |`1e-10` |Relative residual target for each inner CG solve.
|`SolveConfig.cgMaxIterations` |`0` |Use the automatic iteration limit; a positive value sets an explicit limit.
|`CgConfig.primalRegularization` |`1e-8` |`Rp`; LP iterations cap it relative to the smallest slack-to-primal ratio. QP retains the configured value to stabilize uncurved directions. Must be finite and positive.
|`CgConfig.dualRegularization` |`1e-8` |Maximum `Rd`; capped relative to each nonzero normal-equations diagonal. Must be finite and positive.
|`CgConfig.preconditionerRank` |`0` |Choose rank adaptively. A positive value requests that rank, subject to safety caps.
|`CgConfig.preconditionerMemoryBytes` |256 MiB |Limit driver memory for partial-Cholesky factors. Zero forces diagonal preconditioning.
|===

The affine predictor uses `q = -x*s`; the corrector uses
`q = -x*s-dxAff*dsAff+sigma*mu`. Both share the operator and preconditioner. The regularized
operator supports dependent feasible equality rows, while the direct backend requires full row rank.
Nonpositive, nonfinite or underflowed weights fail explicitly.

=== Preconditioner and inexact solves

The adaptive preconditioner starts with the regularized diagonal (Jacobi). When an inner solve misses
its tolerance, the solver builds a low-rank approximation using up to 50 partial-Cholesky columns and
doubles the rank after further failures. Each selected column requires one distributed pass. Later
outer iterations keep the selected rank but rebuild factors for the new weights.

The memory budget and the driver-work limit `m*rank^2 <= 2e10` can reduce an explicitly requested
rank. A pivot at or below `max(min(Rd), 64*ulp(max(diag(G))))` stops factorization. This changes only the
preconditioner; it does not modify the model or add a hidden regularization retry.

Each inner residual component must satisfy
`abs(residual_i) <= max(cgTolerance*max(abs(rhs_i), smallestNonzeroAbsRhs),
0.1*tolerance*(1+min(abs(b))))`; initialization uses only the relative term.
This prevents a large equation from hiding an inaccurate small equation. Outer convergence also
checks each constraint relative to its own RHS.
After exhausting recovery steps, the solver accepts an inexact direction only when its finite true
residual is no greater than `max(cgTolerance*norm(rhs), absoluteTarget, 1e-3*norm(rhs))`.
Otherwise it reports a numerical failure
unless the last completed iterate supplies a valid certificate. `CgConfig` affects only
`ConjugateGradient`; `Cholesky` ignores it.

== Convex quadratic objectives

Continuous models support `0.5*x^T*Q*x + c^T*x + k` with linear constraints.
`QpObjective.separable` supplies diagonal entries of `Q`; `QpObjective.squared`,
`squaredDeviation` and `sumSquares` supply positive-semidefinite sparse factors. See
xref:usage.adoc#_convex_quadratic_objectives[the quadratic-objective API].

Minimization requires nonnegative curvature; maximization requires nonpositive curvature. Quadratic
constraints and quadratic objectives containing `Integer` or `Binary` variables are unsupported.
Repeated terms add, missing diagonal keys contribute zero, and invalid keys, curvature or nonfinite
coefficients raise `LpModelException`.

For a lower-bound shift `x = l + y`, compilation applies
`c' = c + Q*l` and `k' = k + c^T*l + 0.5*l^T*Q*l`. Fixed variables fold into the constant. A curved
variable without a lower bound is rejected because splitting it would introduce coupled curvature; a
zero-curvature variable keeps the linear-model behavior.

=== Solver equations and optimality

For diagonal `Q`, the Newton weight becomes `W = (S/X + Q + Rp)^(-1)`. Stationarity uses
`A^T*lambda + s - c - Q*x`; the primal objective is `0.5*x^T*Q*x + c^T*x`; and the dual expression
is `b^T*lambda - 0.5*x^T*Q*x`. Convergence requires primal, stationarity and quadratic objective-gap
residuals within `SolveConfig.tolerance`; these are the standard convex-QP optimality conditions
described by Stellato et al. <<stellato2020>>. A candidate unbounded direction must also satisfy
`Q*d = 0`, and classifying unboundedness still requires a feasible point.

=== Sparse squared-expression factors

A squared-expression term `w*(a^T*x + t)^2` contributes `Q = 2*w*a*a^T`. A nonnegative `w`
proves nonnegative curvature. The API accepts these terms instead of arbitrary entries in the
quadratic coefficient matrix. Repeated coefficients and terms add; the solver does not construct a
dense quadratic matrix or its inverse.

For each factor, compilation introduces `u, v >= 0`, the equality `a^T*x+t = u-v` and the diagonal
penalty `w*(u^2+v^2)`. At the minimum, at most one of `u` and `v` is positive, so the penalty is
exactly `w*(a^T*x+t)^2`. Each factor adds two internal columns and one row.

Auxiliary rows use the reserved `__qp_factor_*` prefix in internal diagnostics. They are created for
each compilation and do not modify the `LpProblem` or appear as user variables in `solution.value`
and `solution.values`. For coupled factors containing variables without lower bounds, `Auto`
selects regularized CG and explicit `Cholesky` is rejected because the split-variable system can
become singular near convergence.

== Solve evidence

`LpSolution.evidence: Option[LpEvidence]` can contain evidence for an infeasible or unbounded
continuous solve. It is `None` for optimal, stopped and mixed-integer results.

[cols="2,3",options="header"]
|===
|Evidence type |Contents
|`InfeasibilityCertificate` |Original-row multipliers and distributed lower- and upper-bound multipliers.
|`UnboundedDirection` |An improving direction in original variable units and, for proven unboundedness, a feasible point.
|===

Call `evidence.verify(tolerance)` to recompute the certificate against the materialized
original-model snapshot. Verification checks keys, finite values, multiplier signs, stationarity,
feasibility and normalization without trusting solver status or internal residuals. Checks use
absolute original units, so model scale and cancellation affect a suitable tolerance. Evidence is a
floating-point witness, not an exact-arithmetic proof, an irreducible infeasible set or a MIP proof.

=== Infeasibility certificate

`InfeasibilityCertificate.rows` contains original row multipliers.
`InfeasibilityCertificate.bounds` is keyed by
`(setIndex, encodedKey) -> (lowerMultiplier, upperMultiplier)`. Fixed variables are retained;
presolved or merged rows have zero multipliers; and split variables are recombined into original
units.

The sign convention is
`A^T*y + lower + upper = 0` and `b^T*y + l^T*lower + u^T*upper = 1`. A `<=` row or upper-bound
multiplier is nonpositive; a `>=` row or lower-bound multiplier is nonnegative; an equality
multiplier is unrestricted; and a missing-bound multiplier is zero.

=== Unbounded direction

`UnboundedDirection.direction` is zero for fixed variables and normalized to improve the original
objective by one. `UnboundedDirection.point` is present when the solver also proved primal
feasibility. Without that point, `verify` returns `valid = false`: a direction alone cannot
distinguish an unbounded model from an infeasible one. To attach a separately obtained original-model
point, use `proof.copy(point = Some(values))`.

=== Quadratic models

For a quadratic model, the direction must also satisfy `Q*d = 0`. Coupled objectives expose their
factor-expanded internal model, including named auxiliary rows and variables.

Evidence owns persisted Spark data. Complete Spark actions on it before calling `solution.close()`,
which releases the solution and evidence snapshots.

== Progress and cooperative stopping

`SolveConfig.control: SolveControl` applies to continuous solves. Callbacks run synchronously on the
Spark driver. Stop requests are checked between safe solver operations; they cannot interrupt an
active Spark action or native call. `SolveControl.timeLimit` starts after model compilation and does
not include result reconstruction.

Stagnation detection is disabled unless `SolveControl.stagnation` contains a `StagnationConfig`:

[cols="2,1,3",options="header"]
|===
|Setting |Default |Meaning
|`patience` |`10` |Completed outer iterations allowed without meaningful progress.
|`absoluteImprovement` |`1e-10` |Absolute part of the improvement threshold.
|`relativeImprovement` |`1e-3` |Relative part of the improvement threshold.
|`innerPatience` |`100` |CG steps allowed without meaningful true-residual improvement.
|`maxInnerSteps` |`2000` |Maximum CG steps for one RHS across restarts and rank changes.
|===

Before a feasible candidate exists, outer progress uses original-model constraint violation and the
primal, dual and gap residuals. After one exists, objective improvement also counts. For a current
best value `best`, meaningful improvement is
`absoluteImprovement + relativeImprovement*abs(best)`. A stalled or capped inner solve requests
`StopReason.NoProgress` and discards its unfinished direction.

See xref:usage.adoc#_progress_and_cooperative_stopping_continuous_models[the progress API] for
callbacks, metrics, cancellation and candidate ownership.

== Integer and binary models

A model containing `Integer` or `Binary` variables is solved by branch-and-bound. Each search node
sets tighter integer bounds and solves an LP relaxation. The compiled matrix and objective are reused;
node bounds change the RHS and objective offset. Optional cuts add temporary rows and slack columns.

[source,mermaid]
----
flowchart TD
  Q[Take node with best lower bound] --> B{Bound cannot beat incumbent?}
  B -->|Yes| N[Discard node]
  B -->|No| L[Solve LP relaxation]
  L --> I{Feasible integral point?}
  I -->|Yes| C[Check rounding and update incumbent]
  I -->|No| F[Branch on fractional variable or split interval]
  C --> N
  F --> N
  N --> E{Queue empty or node limit?}
  E -->|No| Q
  E -->|Yes| R[Report incumbent and search status]
----

For minimization, a converged relaxation supplies a lower bound and an integer-feasible incumbent
supplies an upper bound. A contradictory node or an infeasibility certificate discards that node. A
fractional value `v` creates children `x <= floor(v)` and `x >= floor(v) + 1`. A near-integer
candidate is rounded only after the original constraints have been rechecked, and the reported
objective includes the rounding change.

[cols="2,1,3",options="header"]
|===
|`MipConfig` setting |Default |Effect
|`maxNodes` |`1000` |Maximum number of launched search nodes. Cut re-solves and strong-branching probes do not count.
|`integralityTolerance` |`1e-6` |Distance from an integer accepted as integral.
|`gapTolerance` |`1e-9` |Relative objective-gap tolerance.
|`absoluteGapTolerance` |`0.0` |Absolute objective-gap tolerance.
|`control` |`MipControl()` |Progress callback, stop callback and optional time limit.
|`sosZeroTolerance` |`1e-6` |Absolute value treated as zero when validating SOS groups.
|`search` |`MipSearchConfig()` |Cut, strong-branching and parallel-search controls.
|===

The result is optimal when no unresolved node can improve the incumbent beyond the configured gap.
Exhausting `maxNodes` with unresolved nodes retains any incumbent and reports `IterationLimit`.

Example: maximizing integer `x+y` with `2*x+2*y <= 3` has an LP-relaxation optimum of `1.5`;
branching finds the integer optimum `1`. Search can grow exponentially. Distributed relaxation solves
do not make an arbitrarily large integer search inexpensive.

== Optional mixed-integer search policies

`MipConfig.search: MipSearchConfig` controls cutting planes, strong branching and parallel node
solves. By default, all three are disabled: the solver processes one best-bound node at a time,
branches on a most-fractional variable and adds no cuts. Branch and tie handling are deterministic for
a fixed compiled model; Spark input order and floating-point reductions can still change numerical
results.

=== Binary knapsack-cover cuts

The implemented cut family is binary knapsack covers. Eligible integral columns must have a
unit-width bound interval at the current node. General integer variables may tighten the capacity but
are not converted to binary variables. A generated cut must be violated by the current relaxation.
The solver does not implement other standard cut families: Gomory, MIR or lifted-cover cuts.

Root cuts are globally valid. A cut generated below the root records that node's integral bound domain
and is inherited only by descendants inside that domain. Duplicate, round, per-node and whole-search
budgets limit separation. Appended cut slacks are removed when converting the relaxation result back
to original compiled coordinates. Every incumbent is checked against the original constraints and
special ordered set (SOS) groups.

=== Strong branching

Strong branching solves bounded trial relaxations for both children of selected fractional variables. A
converged trial can strengthen a child bound; an infeasibility certificate can discard a child. An
incomplete or numerically failed trial retains the parent bound. Trial iterations count against the
probe budgets and do not produce incumbents.

=== Parallel node solves

`MipSearchConfig.parallelNodes` defaults to `1`. A larger value creates a fixed worker pool, while
one driver coordinator owns the search tree, incumbent and global bound. Launched nodes reserve the
node budget. Completion order can change branching, tie choices, node count and elapsed time.

Cancellation remains cooperative. Started Spark operations finish or reach a solver stop check before
workers drain and resources are released. No bound is inferred from an incomplete iterate. User
callbacks run on the coordinator thread.

`MipSearchConfig.maxConcurrentLocalBytes` defaults to 1 GiB and guards estimated concurrent driver
Newton storage. The estimate is `16*m*m + 128*m` bytes per Cholesky relaxation or
`128*m + cgConfig.preconditionerMemoryBytes` per CG relaxation, adjusted for active relaxations and
the maximum cut-row count. `MipSummary.search.estimatedPeakLocalBytes` reports the estimate. It is
not a total JVM or executor-memory limit; Spark caches, shuffles, distributed matrices and model
metadata require additional memory.

Branch-and-bound follows Nemhauser and Wolsey <<nemhauser1988>>. The cut implementation uses the
cover-inequality theory summarized by Kaparis and Letchford <<kaparis2011>>. SCIP's full
strong-branching documentation <<scipStrongBranching>> describes the general probing technique;
spark-lp uses its own bounded policy and does not embed SCIP.
